# ADR 0009: Rotation transforms are measured against the renderer, not derived

* Status: accepted
* Date: 2026-10-09
* Deciders: implementation
* Amends: ADR 0008
* Refines: spec §8

## Context

ADR 0008 fixed the coordinate contract: store normalised coordinates with the
origin at the top-left of the *displayed* page, and express every mapping as an
explicit `AffineTransform`. The contract was right. The implementation of one
transform inside it was not.

`PageGeometry.raw_to_display` composed a y-flip with a clockwise quarter turn. On
an unrotated page it produced the correct answer, which is why it survived: the
most common case looked perfect. On a page with `/Rotate` of 90, 180 or 270 it
produced the wrong origin for **every** rotation, and for two of them it also
mirrored the page left-to-right. A page rotated by a quarter turn would have
rendered correctly while every anchor on it pointed at the wrong place.

The corpus deliberately contains rotated pages. The bug was still not caught,
because there was no test that derived the expected mapping from anything other
than the transform itself.

## The measurement problem

Establishing the correct transform took several attempts, and each failure is
worth recording because they are all easy to repeat:

1. **A least-squares fit over four corners of a rectangle is rank deficient.**
   The four corner points are affinely dependent, so the design matrix has rank 3
   and `numpy.linalg.lstsq` returns a solution that does not reproduce the inputs.
   The fitted coefficients looked plausible and were used to justify a wrong
   conclusion. Fitting a transform requires the points to span the plane; corners
   of a rectangle do not.

2. **`Page.draw_rect` does not take raw PDF coordinates.** It takes the page's own
   system, origin at the top-left of the unrotated media box with y increasing
   downwards. Markers intended for the raw bottom-left were drawn at the page's
   top-left, so the comparison was between a predicted bottom-left point and a
   measured top-left one.

3. **A mean-based marker locator is biased by antialiasing.** The ring of
   partially covered pixels is not symmetrically distributed once a marker has
   been rotated and resampled, so the centroid drifts from the marker's centre.
   Using the bounding box of the matched pixels removed the drift.

4. **Thresholding grey values admits background.** A tolerance wide enough to
   capture a light-grey marker also captured near-white background, which pulled
   the reported position toward the image centre and produced measurements that
   were not marker positions at all. Colours fixed this: a hue test on a channel
   cannot be satisfied by grey background.

## Decision

**The rotation transform is defined by measurement against the renderer, and the
measurement is kept as a test.**

`scripts/derive_rotation3.py` renders one dark marker per page in a known raw
corner and locates it in the resulting pixels. One marker per render removes any
possibility of confusing one marker with another, and the reported position is an
average over the marker's extent, so the answer is not sensitive to a single edge
pixel. `scripts/fit_rotation.py` solves the affine map from those positions; the
fit is exact (rank 3, maximum error 0.000000), and the resulting closed form is
what `raw_to_norm` implements:

| `/Rotate` | mapping, with `w`/`h` the visible size and `x0`/`y0` the crop origin |
| --- | --- |
| 0 | `((x - x0)/w, 1 - (y - y0)/h)` |
| 90 | `((y - y0)/h, (x - x0)/w)` |
| 180 | `(1 - (x - x0)/w, (y - y0)/h)` |
| 270 | `(1 - (y - y0)/h, 1 - (x - x0)/w)` |

`tests/unit/test_rotation_geometry.py` repeats the measurement as a test:
markers in four distinct colours are drawn at known raw positions, the page is
rendered, and the transform's answer for each marker must land within two pixels
of where the marker actually is. The test also requires the four markers to stay
distinct and to keep their relative arrangement, so a transform that collapsed
points together could not pass by agreeing on average.

## Alternatives considered

**A. Derive the transform from the PDF specification.** Correct in principle and
how the first attempt was written. Rejected as the *primary* method because it
depends on a convention (does `/Rotate 90` turn the page clockwise or
anticlockwise in this engine's renderer?) that the specification states but that
an implementation may interpret differently. The measurement settles the
question; the specification explains the result.

**B. Pin the corner mapping as a hand-written table in the test.** Simple, and
what was tried. Rejected after it produced three successive rounds of wrong
expectations: hand-transcription of a geometric fact is itself error-prone, and a
wrong table that agrees with a wrong implementation enshrines the bug. The table
that remains is generated by `scripts/gen_corner_table.py` from the verified
transform, and `test_the_mapping_table_agrees_with_the_transform` checks it
against the implementation so the two cannot drift apart.

**C. Assert only that the unrotated case is correct.** Rejected: this is exactly
the state the bug was found in, and rotated pages are in the corpus because real
scanned documents contain them.

**D. Measure against the renderer, and keep the measurement as a test.** Chosen.

## Consequences

* Rotated pages are now anchored correctly. This is a correctness fix to a feature
  that had no correct implementation, not a refinement.
* The test suite depends on PyMuPDF to verify its own geometry. This is acceptable
  because PyMuPDF is already a project dependency and is the engine whose output
  the transform must agree with; a test that did not use it would be checking the
  transform against nothing.
* A change to the transform now fails a test that measures pixels, so the failure
  message names the marker, the rotation and both positions rather than an
  abstract matrix difference.
* The measurement scripts are retained. They are the evidence for the table, and
  re-running them after any renderer upgrade is the way to detect a change in
  convention.

## Verification

* `python scripts/derive_rotation3.py` prints the measured position of each raw
  corner for each rotation.
* `python scripts/fit_rotation.py` reports an exact fit (rank 3, error 0.000000)
  and confirms the closed form reproduces every measurement.
* `python scripts/check_rotation.py` checks all 16 corner mappings, plus
  round-trip and range properties; it prints PASS or FAIL with counts.
* `python scripts/check_rotation.py --verify` delegates to the pixel test, so the
  table it holds can be re-measured rather than trusted.  That table went stale
  once and reported the rotated cases as failures while the implementation was
  already correct, so `tests/unit/test_rotation_geometry.py` now asserts the table
  against the implementation as well.
* `python -m pytest tests/unit/test_rotation_geometry.py` re-measures from pixels
  and passes for all four rotations.
